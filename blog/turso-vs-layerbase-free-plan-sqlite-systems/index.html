Turso vs Layerbase Free Plan sqlite Systems

October 19, 2026 · Yapern

Turso’s endpoint handled 2,266 point reads per second in a clean twenty-second run. Layerbase’s best clean confirmation was 113. Switch the workload to individual inserts, though, and the order flips: Layerbase reached 125 rows per second in a short stage, while Turso sustained 55. A single “database speed” number would make a mess of this comparison.

I asked Codex to build a schema, fill it, and increase the number of requests in flight against each service. Both eventually returned HTTP 429. On Layerbase, a plain SELECT 1 kept failing after the write load had stopped. A comparison of peak rates would miss that part.

I have no affiliation with Turso or Layerbase. Both databases were on their providers’ Free plans.

The same rows, the same HTTP requests

Each database started empty. The seed was 10,000 users, 2,000 projects, and 100,000 events, with primary keys, foreign keys, unique emails, and indexes for finding recent events by user or project. A fourth table collected benchmark inserts. Every inserted payload contained 256 ASCII bytes.

The client was Node.js 22 on the same macOS machine for both tests. It reused TCP/TLS connections and sent one SQL statement through the Hrana HTTP pipeline per request, followed by a stream close. This measures a hosted libSQL-compatible API, including the network and request handling. It doesn’t measure SQLite opening a local file.

Each concurrency level got a two-second warmup and an eight-second measurement. The best clean level then got a twenty-second confirmation. Workers waited for a response before sending another request; failed requests weren’t retried. In-flight work was allowed to finish, and that drain time counted in the throughput denominator. HTTP errors, SQL errors, and incorrect returned rows all counted as failures.

The logs record SQLite 3.45.1 on Layerbase and 3.47.0 on Turso. Server regions, CPU allocations, and storage settings weren’t controlled, so this compares the two hosted offerings as tested rather than identical server resources.

Those durations matter. Layerbase’s 125 inserts per second came from an eight-second ramp stage; its later confirmation failed after overload. And the roughly twentyfold gap between the best point-read results uses different concurrency levels. At a matched 64 concurrent requests in the eight-second ramps, Turso delivered 793 point reads per second and Layerbase delivered 86.

Adding clients helped reads much more than writes

Turso’s read curve kept climbing as more requests were allowed in flight. Its insert curve flattened around 50 to 55 requests per second. Going from 32 to 128 concurrent inserts mostly bought a longer wait, with p95 latency rising from about 715 milliseconds to 2.8 seconds in the short stages.

The missing Layerbase points at 128 aren’t zero-throughput measurements. Those stages had errors and don’t belong on a clean-throughput curve. Turso’s later 192-concurrent read check also isn’t plotted here, because it came from a separate follow-up run.

There’s a familiar SQLite constraint in the background: ordinary SQLite serializes writes even when WAL lets readers proceed alongside them. That doesn’t identify the bottleneck in either hosted service. These logs can’t separate writer contention, commit handling, storage, or service admission control. They do show when increasing concurrency stopped improving this client’s write rate.

A hundred rows changes the job

For an import, I don’t particularly care how many HTTP responses arrive per second. I care how many records have been saved. The batched test kept the same payload, foreign key, and indexes, but put one hundred rows into a single atomic INSERT.

Turso handled about 42 of those requests per second, down from 55 single-row requests. Each successful batch saved a hundred rows, producing 4,169 inserted rows per second. Calling that “4,169 writes per second” without the batch size would be misleading. It would sound like four thousand independently acknowledged transactions.

The other completed Turso workloads fit that write-rate picture. Atomic counter updates sustained about 60 per second. An 80% read, 20% insert mix sustained 278 operations per second, including roughly 56 inserts per second. A faster read path didn’t make the mixed workload behave like the read-only test.

After the runs, the database contained all 219,157 acknowledged new rows, and the counter sum matched all 4,010 acknowledged updates. Payload-length checks, foreign-key checks, and quick_check passed. Those checks establish that the acknowledged test writes were present afterward; they don’t simulate losing the server or its storage.

The next query after overload

Layerbase’s 128-concurrent insert stage produced 128 client timeouts at the fifteen-second deadline. Follow-up requests began returning HTTP 429 with this response:

{"error":"Timed out while opening database connection"}

The load was stopped. Ten later health probes, ending more than five minutes after it stopped, still couldn’t execute SELECT 1. That prevented final write verification, and it prevented measuring Layerbase’s updates, mixed traffic, or batch inserts. The 297 insert attempts without an acknowledgement have uncertain outcomes; a timeout doesn’t prove the write wasn’t committed.

There’s an important limit on that result: Layerbase’s published Free plan lists 20 concurrent connections. This client went well beyond that allowance. HTTP requests, Hrana streams, and the platform’s connection accounting aren’t interchangeable, and the logs don’t show how that cap was applied. The failure is an observation about deliberate overload, not evidence that the plan promises 128 simultaneous writers.

Turso also pushed back. At 256 concurrent reads, the short stage returned 257 HTTP 429s out of 23,982 attempts, about 1.1%. A longer check at 224 had 198 out of 52,915, about 0.37%. Its response identified load shedding; the database hostname is redacted here:

{"error":"load-shed for host [database-host]"}

At 192 concurrent reads, Turso confirmed 2,266 successful queries per second with no errors. Health and integrity queries succeeded after each run. Its 128-concurrent insert stage also completed without errors, though at about 51 rows per second.

I wouldn’t turn these episodes into uptime statistics. The Turso 429s came from reads; Layerbase’s prolonged failure followed writes. There was one tested endpoint per provider and no server-side trace.

What the free plans actually include

The public offers, checked on October 19, 2026, put different limits around a small application. The monthly row allowances describe how much work is included. They don’t tell you how quickly a burst will finish.

Layerbase also advertises sleep after fifteen idle minutes and a 10 GB per 24 hours acceptable-use allowance on Free-plan bandwidth. “No row meter” doesn’t mean infinite throughput. On Turso, rows read can include scans beyond the rows returned. Our count of successful HTTP requests, and even our count of saved application rows, shouldn’t be substituted for a billing usage report.

Enough evidence to repeat the test

The benchmark bundle includes the schema, a runnable client, the plotting script, and six JSON report snapshots with database hostnames removed. It records the failed stages as well as the clean ones. The current runner stops remaining load on a timeout or HTTP 429; that circuit breaker was added after the first Layerbase run, which was stopped manually.

For the full Turso workload on fresh benchmark tables, set TURSO_URL and TURSO_AUTH_TOKEN in a local .env, then run the downloaded client from its containing directory. Add --reuse only when intentionally testing the already-populated benchmark tables:

node run.mjs --provider=turso --max-concurrency=128

These were short, warmed stages against a roughly 34 MB seed database. They don’t establish sustained production capacity, cold-start behavior, or performance on a multi-gigabyte dataset. A stronger next run would record the server allocations and regions, run longer, and repeat the write-overload test with server metrics.

For a project like Yapern, I’d measure opening a thread and saving a reply before choosing a host from the largest read number. This run gives Turso a strong read result and a complete, verified write test. Layerbase’s higher short insert rate deserves a longer confirmation and another recovery test before I’d build a decision around it. The next ordinary query needs to work after the benchmark client has gone away.
